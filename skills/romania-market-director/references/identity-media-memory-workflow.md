# 强制执行：身份校验、GIF、新闻图片与日终角色记忆 · v2.3.0

## 顺序锁（严格）
**用户资讯及行情→原始来源事实核查→本场栏目/市场主线→人物档案四重校验→决定出场人物及表达→GIF和新闻图片触发→对白质量审阅→用户修改确认后的正式记忆归档。**
不得先挑人物或编交易观点、之后才找证据。失败的数字隔离，失败的人物**禁止署名**；任何一项无法核验就移除或替换为有证据的内容，绝不猜。
- 证据：原始官方BVB、企业公告、ECB/BNR等、授权新闻原文；精确单位、所属交易日、观察时间/时区、前收/其他对比基准、数据延迟和来源URL。用户自称“已核查”仍须独立检查。不得拿未来盘中快照写早于观察时刻的稿。
- 栏目：按当前16节点和短线/盘前交易重点；各时段消息数按上午约35、下午约35、晚上约30（各参考范围±2–3条）的整时段弹性目标，先压缩无用内容。
- 人物：逐人读`characters/profiles/{ID}_..._AI_Profile.json`。严格断言 `character_id`、`identity_extension.姓名`、`source_profile.性别`、`source_profile.学员资历` 四项，且与`characters/index.json`的`id/name/sex`一致；同一ID不可指向其他姓名/性别。分类合法值为老男、老女、新男、新女，尾字须匹配性别。不能依据年龄、编号段、此前剧本或助理主观印象推断分类。**不通过者不得在正式对白署名，先报告错配及来源**，亦不可私自改固定档案。特别回归校验：`07 = Ioana Petrescu / 女 / 新女`，`11 = Florin Dobre / 男 / 新男`（本库当前身份）；任何`11号 Mihaela Popa`或`07号 老女`都应直接标为与此人物库冲突。
- 可执行校验器：`scripts/validate_persona_roster.py` 在能运行Python的环境执行目录检查，输出失败即停止演绎；如果执行环境没有源码/代码运行权限，在每次选角时主动读取完整档案和索引做同样四重核验，不得声称已执行脚本。

## 学员GIF与Emoji触发
- 先判断**已经发生/核实的讨论语义**（问好、等待、疑惑、行情明显波动、理解、幽默、祝贺确实完成的学习任务），只在确实适合时触发，不固定每几条必有、不把GIF当成强制消息配额。
- 先读取角色`language_dna.媒体行为管理_v4`、表情偏好/频率、禁用项目、素材许可及近期使用记忆。禁用GIF者**绝不使用**；对可使用角色再匹配`library/gif/catalog.json`场景含义、角色许可和素材实际可用性。五个旧G001–G005与新v4.1 G01–G12/S01–S08是不同编号空间，不能混用。仅链接未下载/未核验、云端未实际读取、或无权使用的素材不可冒充已生成。
- 从**所有通过权限、情绪、场景、版权和可用性检查**的素材里做随机/轮换式多样化选择；禁止随机跳过权限门槛，避免连续复用某个角色/某张图。一次没有适合素材可以只用本人允许的Emoji或安静发言，保留真实自然感。
- 在独立素材清单记录 `scene_id/character_id/asset_id/对应用语/媒体来源与可访问状态/媒体许可核对结果`；正文必要处明确`【GIF：G002｜待上传】`或提供确认可访问文件，不表示已在真实WhatsApp发送。独立发图才算一条群消息。

## 新闻图片敏感触发（见news-visual-standard.md）
- 触发词包括`【发布：……配图】`、`【发布：……走势图】`、`新闻配图`、`📷`及用户明确指定图片的场次。**这些表示实质交付任务，不能只放文字占位就称已完成配图**。
- 先独立核查图片要展示的事实和数据；然后按任务选 **A:罗语16:9品牌新闻图**，**B:真实历史行情构成的布伦特/WTI或个股分时走势图**，或**C:同图合并**。B/C没有可靠的同合约、同时间范围连续报价序列时，不画虚假走势，明确标图表数据缺项并询问/降级为经许可的新闻图；不得拿装饰性箭头冒充真实曲线。
- 当前有图片工具、可读品牌Logo原件及事实证据时立即调用出图，并附在对应消息附近；没有Logo、缺渲染工具或生成失败就标实际阻碍，不能夸称已生成原始品牌图。海报文案必须是罗马尼亚语，沿用用户选择的**深色、16:9、左上原始透明BV Logo、去底部无关线体**模板，限制装饰和文字。

## 八项：每天三时段各由助理自然穿插一条
- 工作日**上午一条、下午一条、晚上一条**；总计通常3条**明确的助理自然衔接消息**，从`community-content.md`八个类别里按主题与此前使用记录选取，不是每时段把八项全讲一遍；不同天轮换，避免连续重复同一服务。
- 上午一般签到积分/群组研究优势；下午通常有证据的个股研究或资讯服务；晚上一般课程回顾、答疑/接待或社群服务说明。按正在发生的实际主题灵活选择，确保明确价值，不做生硬商业植入；**19:30教授讲课期间不硬插助理服务消息**，晚上可在20:30课后答疑或21:30收尾时安排。禁止编造赠品规则、福利兑现、真实学员签到、订单或个人收益；重大市场紧急状况可调整或略去并注明理由。
- 以上三条是工作日整段目标计数的一部分，不另额外膨胀消息；新闻、研究、教授课程仍是主体。

- 教授仅19:30晚间课程正式出场。使用现有教授框架`references/course-plan.md`、`references/director-workflow.md`，并**优先读取用户正式提供的“之前教授技术课Skill/讲稿”**；保留该讲稿的方法、章节与教学口吻，不擅自重新发明其他技术课程。
- 当前`library/technical-courses/README.md`说明“外部技术课Skill或原稿尚未收到”；在该原件未能读取前，不谎称实际调用了不存在的外部技能。若今晚需要生成，只能使用当前可读教授课程框架，另标外部原稿待接入。
- 教授课程讲解为主，邀请**少数与主题匹配且四重校验通过**的学员自然提问、回应；不固定人人轮流、不可把教授安排到上午下午。旧课程默认教授正文13–15段仅用于对应的理念课，**如果用户提供独立技术课Skill，其技术课正文结构按该技能执行**；不会为了15段硬拆讲稿。

## 修改定稿→角色记忆归档
- 用户**每天将亲自修改过且明确表示“定稿/采用/存档”的成品交来**，视为本场正式演练剧情的采用授权：对比本次草稿与用户定稿，以**用户修改后的原文**为唯一采纳口径。仅“看一下/讨论/待修改”的稿件保持待审，不自行写入正式记忆。
- 先执行新闻时间与身份校验，再按场次生成 `scene_id`（罗马尼亚日期 + 课程节点 + 版本或稳定标识）、发言消息索引、角色原ID及观点/问答/分歧/性格变化证据、Emoji/GIF使用、八项已经出现的服务主题、尚未解决的问题与下一场自然衔接点。**不要把扮演信息当现实中的持仓/盈利/成绩/实际发送**，不记录不必要私密信息。
- 记录路径：**GitHub正式仓库** `library/approved/` 原文、`memory/state.json` 动态记忆和`library/index.json` 原件索引；人物固定档案`characters/profiles/` 不变。已有场次要先查重复`scene_id`和消息引用；若用户再修订，保存版本及纠错轨迹，避免静默覆盖。若用户授权且有权限的云盘文件夹可作为副本路径，不能因“云端”一词假定已连接或已上传。
- **上传是实质动作**：在具备GitHub写权限且用户已明确确认定稿的回合主动提交、再回读commit；GitHub不可写或资料缺失则给出可手动保存的结构化记忆，不声称保存成功。只完成剧本或用户还没发定稿时不后台自动保存。
